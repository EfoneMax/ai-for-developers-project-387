# Календарь звонков

Сервис бронирования встреч по мотивам [Cal.com](https://cal.com). Владелец календаря публикует доступное время, а гость без регистрации выбирает свободный слот и записывается на звонок.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers  
Как это должно работать: https://files.hexlet.app/a/2ipc5m

[![hexlet-check](https://github.com/EfoneMax/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/EfoneMax/ai-for-developers-project-387/actions)

Это вторая часть проекта: приложение перенесено из
[`EfoneMax/ai-for-developers-project-386`](https://github.com/EfoneMax/ai-for-developers-project-386),
где были спецификация и архитектурные решения. Трекер задач — GitHub Issues
этого репозитория.

## Сценарий гостя и владельца

### Владелец

1. Открывает кабинет владельца.
2. Создаёт тип встречи: название, описание и длительность.
3. Тип сразу появляется на публичной странице.
4. В разделе предстоящих встреч видит все записи гостей: дату и время по Москве, тип встречи и контактные данные гостя. Если гость выбирал слот в другом поясе, рядом показан IANA-id его пояса и местные дата и время.
5. При необходимости отменяет предстоящую встречу: запись исчезает из списка, а слот снова становится свободным.

### Гость

1. Открывает публичную страницу без регистрации.
2. Выбирает тип встречи.
3. Открывает календарь на 14 дней и выбирает свободную дату и время.
4. Указывает имя, email и при необходимости комментарий.
5. Подтверждает запись.
6. Запись сразу появляется в списке предстоящих встреч владельца, а слот становится занятым.

## Сценарий в Cal.com (референс)

1. Войти в Cal.com и открыть раздел **Event Types** (в актуальном интерфейсе — **Links**).
2. Нажать **New → Event Type**, указать название, описание и длительность, например 20 минут. Сохранить тип встречи.
3. Открыть публичную страницу владельца (`cal.com/<username>`) и выбрать созданное событие.
4. Выбрать дату в календаре и свободное время, нажать **Continue**.
5. Заполнить имя и email гостя, при необходимости добавить заметку, и подтвердить бронирование.
6. Вернуться в кабинет → **Bookings → Upcoming**. Новая запись появится в списке владельца с датой, временем, типом встречи и данными гостя.

> Сценарий проверен на тестовом аккаунте Cal.com: новый тип встречи создан через **New → For myself**, после записи на него бронь появилась в **Bookings → Upcoming**. Для гостевой почты лучше использовать адрес, который реально принимает письма: на одноразовый домен Cal.com может не сохранить бронирование.

## Правила календаря

- Часовой пояс владельца: `Europe/Moscow` (UTC+3).
- Рабочие дни: понедельник–пятница, 09:00–18:00.
- Шаг доступных стартов: 30 минут.
- Окно записи: 14 календарных дней, начиная с сегодняшнего.
- Длительность слота равна длительности выбранного типа встречи.
- Пересечения запрещены, включая частичные и между разными типами встреч.
- Встречи встык разрешены: следующая может начаться в момент окончания предыдущей.
- Одновременные запросы на один слот обрабатываются атомарно.

## Стек и контракт

- **Контракт:** TypeSpec → OpenAPI.
- **Клиентский SDK:** генерируется из OpenAPI для TypeScript-фронтенда.
- **Бэкенд:** Node.js, TypeScript, Fastify. Маршруты реализуются по контракту и проверяются тестами.
- **Фронтенд:** React, Vite, TypeScript, shadcn/ui.
- **Запуск:** Docker; Fastify отдаёт API и собранный SPA с одного origin.
- **Тесты:** Vitest, включая дымовой тест запуска приложения.
- **Хранение:** в памяти процесса; после перезапуска сервера записи и типы встреч сбрасываются.

## Запуск и проверки

```bash
mise run setup      # зависимости, OpenAPI и SDK, Git-хуки
mise run dev        # API и фронтенд как daemons
mise run check      # линтеры, типы, тесты и сборка
mise run check:e2e  # сборка и браузерные сценарии Playwright
mise run check:all  # все проверки: быстрые и браузерные, как в CI
```

`mise run check` не запускает браузер: он укладывается в минуты и выполняется
перед пушем. `mise run check:e2e` собирает проект, поднимает Fastify и
preview-сборку фронтенда и прогоняет Playwright с одним воркером.

API — `http://localhost:3000`, фронтенд — `http://localhost:5173`.
Кабинет владельца — `http://localhost:5173/owner`, он открыт без входа.
Остановить фоновые сервисы: `mise daemons stop`.

CI запускает ту же команду `mise run check:all` одним job на pull request и
push в `main`: браузерный слой идёт после быстрых проверок внутри одной
команды, поэтому красный линтер не тратит минуты на Chromium. Job ставит
только Chromium, ограничен 25 минутами и при падении сохраняет трейсы
Playwright артефактом. Pre-push hook выполняет только `mise run check`.

## Агент в GitHub Actions

В репозитории подключён [OpenCode GitHub](https://opencode.ai/docs/github):
агент запускается из комментария и отвечает там же, от имени приложения.

- **Файл:** [`.github/workflows/opencode.yml`](.github/workflows/opencode.yml).
- **События:** `issue_comment` и `pull_request_review_comment`, только `types: [created]`.
- **Команды:** `/oc` и `/opencode` (заданы явно в `mentions`).
- **Кто может запускать:** только `OWNER`, `MEMBER` и `COLLABORATOR`; комментарии ботов и недоверенных авторов игнорируются. PR из fork не получают секреты.
- **Модель:** `deepseek/deepseek-flash`; ключ хранится в GitHub Secrets как `DEEPSEEK_API_KEY` и в репозиторий не попадает.
- **Контекст проекта:** агент читает `AGENTS.md` и `docs/agents/`, ведёт задачи в `EfoneMax/ai-for-developers-project-387` (см. `docs/agents/issue-tracker.md`) и проверяет правки командой `mise run check`; полный прогон, как в CI, — `mise run check:all`.
- **Назначение:** разбор issue и обсуждений, работа по скиллам из `.agents/skills/` (`to-spec`, `to-tickets`, `implement-spec`, `code-review`), правки в ветке PR.
- **Результаты:** ответ агентом-приложением в issue или PR и прогон в **Actions → opencode**.
- **Действие:** `anomalyco/opencode/github` закреплён на коммите `77fc88c` (снимок 2026-11-23), раннер `ubuntu-latest`, checkout глубиной 1.
- **Ограничение приложения:** GitHub App не имеет права `workflows`, поэтому изменения в `.github/workflows/` агент не пушит. Такие файлы применяются человеком или локальным агентом после ревью; остальные изменения агент делает сам.
- **Ограничения запуска:** `timeout-minutes: 25`, `concurrency` по номеру issue/PR без отмены уже идущего прогона (`cancel-in-progress: false`), права `contents: read`, `issues: write`, `pull-requests: write` и `id-token: write`, у checkout `persist-credentials: false`. Запись комментариев и ветки идёт через токен GitHub App из OIDC; отчёт `limit_exhausted` публикуется через `gh pr comment`.

Примеры вызова:

```text
/oc explain this issue
/oc запусти скилл to-spec по обсуждению этого issue
/oc запусти скилл implement-spec по этой спецификации
```

Перед первым запуском приложение OpenCode должно быть установлено на
репозиторий, а `DEEPSEEK_API_KEY` добавлен в **Settings → Secrets and variables
→ Actions**.

### Автотриаж новых обращений

- **Файл:** [`.github/workflows/opencode-triage.yml`](.github/workflows/opencode-triage.yml).
- **Событие:** `issues: [opened]` — только новые обращения; правки и комментарии повторный разбор не запускают.
- **Фильтр доверенных авторов:** job выполняется, только если автор — `OWNER`, `MEMBER` или `COLLABORATOR`, а не бот (`user.type != 'Bot'`). Остальные обращения остаются без автоматического разбора.
- **Что пропускается:** issue с меткой `ready-for-agent` — это уже подготовленные `to-spec` и `to-tickets` тикеты, им повторный триаж не нужен.
- **Prompt:** задан прямо в workflow. Агент читает `AGENTS.md`, `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`, `GLOSSARY.md` и `docs/adr/`, работает по скиллу `triage`, проверяет дубли среди открытых issue и существующую реализацию в коде и говорит, где искал. Предлагает категорию (`bug` или `enhancement`), состояние и следующий шаг: при нехватке данных задаёт конкретные вопросы и ставит `needs-info`, готовое обращение получает `ready-for-agent`, дубль или уже реализованное — `wontfix` с объяснением. Код не меняет, PR не создаёт, ответ начинает с дисклеймера из скилла `triage`.
- **Модель и токены:** `deepseek/deepseek-flash`, `DEEPSEEK_API_KEY` и `GH_TOKEN` (`secrets.GITHUB_TOKEN`) — как в `opencode.yml`; действие `anomalyco/opencode/github` закреплено на том же коммите `77fc88c`.
- **Ограничения:** `timeout-minutes: 15`, `concurrency` по номеру issue без отмены уже идущего прогона (`cancel-in-progress: false`), права `contents: read`, `issues: write` и `id-token: write`; у checkout `persist-credentials: false`.
- **Результат:** комментарий от приложения в issue, метки трекера и прогон в **Actions → opencode-triage**.

### Авторевью pull request

- **Файл:** [`.github/workflows/opencode-review.yml`](.github/workflows/opencode-review.yml).
- **Событие:** `pull_request: [opened, synchronize, reopened, ready_for_review]`. Черновики пропускаются.
- **Кто получает ревью:** PR из ветки этого же репозитория от `OWNER`, `MEMBER`, `COLLABORATOR` или от `opencode-agent[bot]`. PR из fork не получают секрет модели.
- **Как работает:** отдельный прогон обычного OpenCode CLI (`opencode run`, версия закреплена в `mise.toml`) готовит текст, следующий шаг публикует его через `gh pr comment`. Ревью не меняет код и не продолжает сессию реализации.
- **Критерии:** [`REVIEW.md`](REVIEW.md), спецификация #7 и согласование в #6, diff PR и результаты CI. Замечание содержит файл, строку, условие ошибки и последствие.
- **Права:** `contents`, `issues`, `actions`, `checks`, `statuses` — read; `pull-requests: write` только для комментария.
- **Ограничения:** `timeout-minutes: 20`, `concurrency` по номеру PR с отменой устаревшего ревью.

### Браузерная проверка PR

- **Файл:** [`.github/workflows/pr-e2e.yml`](.github/workflows/pr-e2e.yml).
- **Что делает:** собирает приложение из точного `pull_request.head.sha`, прогоняет Playwright с `--trace on` и загружает артефакт `e2e-<sha>` с трейсами, HTML-отчётом и файлом `artifact-sha.txt`.
- **Зачем:** проверяющий перед мержем сверяет SHA артефакта с текущим head PR и проходит основной и соседний сценарии спецификации.

### Бюджет запусков агента на PR

- В `opencode.yml` перед вызовом модели выполняется шаг бюджета: он считает прошлые попытки по истории Actions (`run-name` с номером PR и `run_attempt`), а не по комментариям.
- Лимит — 4 попытки на PR. Считаются все запуски по `/oc` и `/opencode`, включая отмены, таймауты и Re-run.
- После исчерпания шаг публикует `limit_exhausted` с последним SHA и ссылкой на лог; модель не вызывается. Бюджет действует только для pull request, не для issue.

## Выводы о работе GitHub-агента

Агент хорошо справляется с рутиной, когда задачи нормально декомпозированы на issue и спеки. Он адекватно проводит анализ, реализацию доработок и PR с тестами. Главные проблемы оказались не в написании кода, а в правах и окружении: у приложения нет прав на изменение воркфлоу-файлов, агенту нужен отдельный `GH_TOKEN`, а headless-режим не умеет подтверждать запросы доступа.

Агенту требуются инструкции, ссылки на спеки, авторевью, настроенный процесс CI. Из изменений запретил менять код на триаже и воркфлоу на реализации.

## Деплой

Публичная ссылка: **https://call-booking-production.up.railway.app**

Сервис развёрнут на [Railway](https://railway.com) из `Dockerfile` в этом
репозитории. Railway передаёт контейнеру `PORT`, Fastify слушает этот порт и
отдаёт и API, и собранный фронтенд с одного origin — отдельный адрес API и
CORS не нужны.

```bash
docker build -t call-booking .
docker run --rm -p 8080:8080 -e PORT=8080 call-booking
# http://localhost:8080 — приложение, /api/health — проверка живости
```

Образ трёхстадийный: на первой стадии собираются контракт, SDK, сервер и
фронтенд, на второй ставятся только production-зависимости, в финальный
образ попадают `server/dist` и `web/dist`. Приложение стартует автоматически
командой `node server/dist/index.js`; `PORT` по умолчанию `3000`.

При старте сервис заводит два типа встреч, если каталог пуст: «Знакомство»
на 30 минут и «Консультация» на 60 минут. Это обычные записи: владелец может
их переименовать, изменить длительность или удалить. Гость может записаться
сразу после открытия публичной страницы.

### MCP-сервер Railway

В проектном [`opencode.json`](opencode.json) подключён удалённый MCP-сервер
Railway (`https://mcp.railway.com`). Секретов в конфигурации нет: вход
проходит по OAuth при первом обращении к инструментам сервера.

1. Откройте проект в OpenCode и выполните `/mcps` — в списке будет сервер
   `railway`.
2. Выберите его и пройдите OAuth-вход в браузере: подтвердите доступ к
   рабочему пространству Railway.
3. Токен сессии OpenCode хранит вне репозитория (в своём хранилище
   авторизации); в Git он не попадает. Повторно входить нужно только после
   отзыва доступа.

Добавить сервер в другой проект можно той же командой, без ключей в
конфигурации:

```bash
opencode mcp add railway --url https://mcp.railway.com
```

Если нужен локальный MCP через CLI, установите Railway CLI и войдите
командой `railway login` (для headless-окружения — `railway login
--browserless`, код подтверждения вводится в браузере). Затем `railway mcp`
запускает MCP поверх stdio. Для повторного выката из корня репозитория:
`railway up`. Если вместо OAuth используется API-токен, передавайте его
переменной окружения `RAILWAY_API_TOKEN` и не добавляйте `.env` в Git.

### Хранение данных

Данные по-прежнему хранятся **в памяти процесса**: типы встреч и брони
сбрасываются при перезапуске контейнера, повторном деплое и перезапуске
сервиса на Railway. Базы данных нет, постоянного диска тоже. Когда каталог
типов пуст, сервис снова заводит «Знакомство» и «Консультацию». Это
ограничение учебной версии, а не настройка хостинга.

## Версии и релизы

Версию и changelog ведёт [release-please](https://github.com/googleapis/release-please) в manifest-режиме: один корневой пакет, `release-type: node`, стартовая версия `0.1.0`.

- `fix:` — patch: `0.1.0` → `0.1.1`.
- `feat:` — minor: `0.1.0` → `0.2.0`.
- Breaking change (`!` после типа или футер `BREAKING CHANGE:`) — major: `0.1.0` → `1.0.0`.
- `chore:`, `docs:`, `test:` и `refactor:` релиз не двигают.

Предусловие: в `Settings → Actions → General` должно быть разрешено
`Allow GitHub Actions to create and approve pull requests`, иначе job `Release`
упадёт при создании PR.

После пуша в `main` workflow `Release` создаёт или обновляет pull request с новой версией в `package.json` и записью в `CHANGELOG.md`. Мерж этого PR создаёт тег `vX.Y.Z` и GitHub Release; вручную теги и релизы не создаются. `CHANGELOG.md` генерируется release-please и исключён из `oxfmt`, а сгенерированный коммит `chore(main): release ...` исключён из правила `references-empty` — у него нет футера `Refs:`.

Пакеты `api`, `server` и `web` приватные: в npm ничего не публикуется, своих версий и релизов у них нет, workspace-версии не бампаются. Версия контракта в TypeSpec (`@info(version: "0.1.0")`) автоматически не меняется.

## Ограничения

- Нет авторизации и личных кабинетов: владелец один и задан заранее.
- Нет интеграций с внешними календарями и уведомлений.
- Нет переноса записи: отменить предстоящую встречу может только владелец.
- Владелец всегда видит время в часовом поясе `Europe/Moscow`; гость — в своём часовом поясе.
- Пояс гостя — необязательный снимок на момент записи. Для записей из другого пояса в кабинете рядом с московским временем показан IANA-id пояса гостя и его местные дата и время; для `Europe/Moscow` и записей без пояса список выглядит как раньше. Пояс не участвует в расчёте доступности.

## Реализация

Реализован полный сценарий: главная страница, кабинет владельца `/owner` с типами встреч и предстоящими записями, страница записи `/book` с календарём свободных слотов, созданием и отменой брони. Контракт TypeSpec описывает типы встреч, слоты и брони, а SDK фронтенда генерируется из OpenAPI. Данные хранятся в памяти процесса, поэтому после перезапуска контейнера сбрасываются.
