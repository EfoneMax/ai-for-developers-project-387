# Бронь хранит снимок часового пояса гостя

**Status**: accepted

**Дата**: 23 ноября 2026

## Context

ADR-0003 зафиксировал, что API не принимает и не хранит пояс гостя, а
владелец всегда видит московское время. На практике владелец не понимает,
в каком поясе гость выбирал слот: одна и та же встреча может быть утром для
гостя и днём по Москве. Без снимка пояса он не может оценить, удобно ли
человеку время, и перепроверить, правильно ли стороны поняли друг друга.

При этом записи из Москвы, старые и сидовые брони без пояса, а также
случаи, когда пояс не определился или оказался невалидным, должны
выглядеть и работать как раньше. Этот документ частично заменяет ADR-0003:
владелец по-прежнему видит московское время основным, а пояс гостя
становится дополнением.

## Decision

- Бронь хранит необязательный `timeZone` — IANA-id пояса, в котором гость
  выбирал слот. Пояс — снимок на момент создания брони, как снимок типа
  встречи по ADR-0006; позже он не пересчитывается.
- `BookingCreate` принимает необязательный `timeZone`, `Booking` возвращает
  его, только когда он сохранён. Ответы без пояса выглядят как раньше.
- Сервер валидирует пояс через `Intl` и сохраняет валидное значение без
  преобразований, обрезав пробелы по краям. Отсутствующий, пустой или
  невалидный пояс не создаёт ошибку валидации: бронь создаётся без пояса,
  слот занимается как обычно. Строгий `400` для этого поля не используется.
- Отмена брони сохраняет снимок пояса.
- В кабинете владельца московские дата и интервал остаются основными и
  видны всегда. Дополнительная строка с IANA-id и местными датой и временем
  гостя показывается, только если пояс сохранён, валиден и не равен
  `Europe/Moscow`. Для Москвы, отсутствующего и невалидного пояса строка не
  показывается, список выглядит как прежде.
- Пояс используется только для снимка и отображения. Внутри сервиса и в API
  время остаются абсолютными моментами UTC, занятость и пересечения
  считаются по ним, а пояс гостя не участвует в расчёте доступности.

## Consequences

- Владелец видит, в каком поясе гость выбирал слот, и может сравнить это
  время со своим московским, не меняя привычный способ читать календарь.
- Гость из Москвы и старые записи без пояса не отличаются от прежнего
  поведения; миграция данных не нужна, хранилище в памяти.
- Невалидный пояс, даже если он каким-то образом попал в данные, не роняет
  рендер: строка просто скрывается.
- Пояс скрывается по IANA-id, а не по текущему смещению. Эквивалентные по
  смещению зоны с другим именем показываются, потому что владельцу важно
  именно то, что гость выбирал слот в другом поясе.
- Клиенты, не отправляющие `timeZone`, получают прежний контракт и прежнее
  поведение.

## Alternatives

- **Хранить пояс в контактных данных гостя**: смешивает контакты и параметры
  встречи; гость существует только внутри конкретной брони, поэтому пояс
  логичнее держать на самой брони.
- **Строгий `400` для невалидного пояса**: необязательное поле не должно
  блокировать запись и занятие слота; мягкая деградация сохраняет
  совместимость.
- **Конвертировать время по поясу гостя на сервере**: API пришлось бы
  принимать и валидировать пояс в каждом запросе, а занятость и окно записи
  по-прежнему считаются по Москве.
- **Показывать пояс гостя вместо московского времени**: ломает привычный
  календарь владельца и противоречит правилу, что основное время —
  московское.
